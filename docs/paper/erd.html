Three things a panel will probe

  • "This is a document database — why an ERD at all?" Because the entities and their relationships are real regardless of the store. What changes is that a subcollection path is the foreign key: users/abc123/outlets/outlet1 already encodes the ownership that a relational schema would need a userID column for. That is why USER appears as the parent rather than as a column on every table.
  • "Why is OUTLET a table if there are only ever two rows per user?" Because the two-outlet limit is a design constraint, not a schema one. The document holds live telemetry that changes every few seconds — it is a record with state, not a lookup value.
  • "Where is the appliance detection stored?" On the user, not the outlet — up to four signatures per appliance. Deliberate: an appliance moved from outlet 1 to outlet 2 keeps its learned profile. Storing signatures per outlet would make the system re-learn the same fan twice.

Draw an Entity Relationship Diagram for WattWise, a smart energy monitoring
system for an apartment room with exactly two switchable outlets. The store is
Cloud Firestore, so ALL primary and foreign keys are strings, never integers.

USER is the root. Almost everything else is a subcollection beneath it, so draw
USER at the centre with its children branching off.

ROOT DOCUMENT
  USER  (users/{userId})
    userId PK string (Firebase Auth UID), name string, email string,
    rateProfileId string, supplyRates map, applianceProfiles array,
    device map, pushTokens array<string>

EMBEDDED IN USER (array, not its own collection)
  APPLIANCE_PROFILE : applianceName key, signatures array (max 4),
                      sampleCount number, updatedAt timestamp

SUBCOLLECTIONS OF USER  (USER 1 --- many, unless noted)
  OUTLET                (outlets/{outletId})        EXACTLY 2 per user
     outletId PK string "outlet1"|"outlet2", outletNumber number,
     applianceName string, status string, pendingStatus string,
     voltage number, current number, power number, energy number,
     energyDateKey string "YYYY-MM-DD", totalEnergy number,
     applianceIdentity map, safety map, relayFault map,
     metricsUpdatedAtMs number, lastUpdated timestamp
  DEVICE_COMMAND        (device_commands/{commandId})
     commandId PK string, deviceId FK string, outletId FK string,
     action string, reason string, source string, delivery map,
     acknowledgment map, metadata map, issuedAtMs number, issuedAt timestamp
  SCHEDULE              (schedules/{scheduleId})
     scheduleId PK string, outlet FK string "1"|"2", type string, time string,
     days array, action string, active boolean, countdownRemaining number,
     lastTriggered timestamp
  POWER_SAFETY          (power_safety/settings)     EXACTLY 1 per user
     id PK "settings", thresholds map {voltage:{min,max}, current:{max},

  HISTORY_LOG           (history_logs/{logId})
