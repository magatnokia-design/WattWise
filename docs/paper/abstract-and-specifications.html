Paste — Abstract

Rising electricity costs, and the limited visibility households have into what individual appliances consume, are persistent concerns for residential users. A monthly electricity bill reports a single total and attributes it to nothing, leaving the household unable to identify which appliance is responsible for a rise in cost. This study designed and developed WattWise: An IoT-Based Dual-Outlet Energy Monitoring and Appliance Control System, which provides residential users with per-outlet measurement, appliance identification, real-time cost analysis on the PELCO III residential tariff, and automated safety cut-off.

The system comprises an ESP32-WROOM-32 microcontroller with two PZEM-004T energy sensors and a two-channel relay module, a Firebase cloud backend providing authentication, document storage and scheduled processing, and two client applications: an Android mobile application and a web dashboard.

A mixed-methods developmental design was employed. Measurement accuracy was assessed quantitatively against a reference clamp meter across N load points, and computed cost was verified against nine actual PELCO III billing statements. System quality was evaluated by thirty intended user respondents, selected by purposive sampling from households within LOCALE, together with a licensed electrician, an electronics technician and an information technology expert, using a questionnaire derived from the ISO/IEC 25010:2011 product quality model across seven quality characteristics.

Metered energy agreed with the reference instrument to within 2.18 per cent, and computed cost agreed with the issued statements to within 0.71 per cent. The intended users rated the system WM (interpretation) overall, rating characteristic highest and characteristic lowest. The technical evaluators rated the system WM (interpretation).

The findings indicate that per-outlet measurement with direct cost attribution is achievable at low cost using commercially available components, and that one sentence on what the users’ ratings mean for the objective. The system is recommended for deployment context, subject to the limitations stated in Chapter I.

PART 02

System Design Specification

Chapter III → after Requirements Modelling

Paste — Chapter III › System Design Specification

The WattWise system is organised into three tiers: a device tier that measures and switches, a cloud tier that stores and computes, and a client tier through which the user observes and controls. Each tier communicates only with the tier adjacent to it, so that no client ever addresses the hardware directly and the hardware holds no user credentials.

Device tier

An ESP32-WROOM-32 microcontroller reads two PZEM-004T energy sensors over separate serial channels and drives a two-channel relay module, one channel per outlet. Measurements of voltage, current, power and cumulative energy are posted over HTTPS to the cloud tier at a fixed interval. The controller holds a device identifier and a device token, and no user account credentials, so that a controller recovered from a household discloses nothing about the account it served. Network credentials are entered once through a setup portal and retained in non-volatile storage.

Cloud tier

Firebase provides authentication, a Cloud Firestore document store, and Cloud Functions deployed to the asia-southeast1 region. The functions fall into three groups: endpoints addressed by the controller, callable functions addressed by the clients, and scheduled jobs that run without a caller — the nightly consumption rollup, the monthly billing statement, and the sweep that times out undelivered commands. Access is governed by security rules evaluated on the server, under which a document may be read or written only by the account that owns it.

Client tier

Two clients present the same account. The Android application is the primary interface and is the only one able to pair a controller by scanning its code; the web dashboard offers the same monitoring, control, analysis and export functions on a larger display. Both read from and write to Firestore through the same security rules, and both compute cost using the same tariff logic, so that a figure shown on one is the figure shown on the other.

Command flow

Commands are not pushed to the controller. When a user switches an outlet, the client invokes a callable function which writes a pending command to the account’s command collection; the controller polls for that command, executes it, and acknowledges the result, whereupon the outlet’s state is updated. A command that is not acknowledged within a fixed interval is marked as timed out, the outlet is returned to the position it held before the command was issued, and the user is notified that the instruction did not reach the device. This design was adopted because a controller behind a domestic router cannot reliably receive an unsolicited inbound connection, and because it makes the failure of a command observable rather than silent.

PART 03

Development Specification

Chapter III → after System Design Specification, before Tables 4 and 5

Paste — Chapter III › Development Specification

The system was developed across three codebases, each with its own toolchain.

The Android application was built with React Native under the Expo framework, in JavaScript, and is distributed as an installable package rather than through an application store. The web dashboard was built with React and the Vite build tool, also in JavaScript, and is served as a static site. The backend was written in JavaScript for the Node.js runtime and deployed as Firebase Cloud Functions. The controller firmware was written in C++ using the Arduino IDE, with libraries for the energy sensors, wireless networking and JSON encoding.

Version control was maintained with Git, with the application and web codebases held in separate repositories sharing one Firebase project. Continuous integration was used to produce the Android package, so that every release is built from a recorded commit in a clean environment rather than from a developer’s machine. Backend logic is covered by an automated test suite executed on each change.

The software and hardware required to operate and to develop the system are stated in Table 4 and Table 5 respectively.

PART 05

Implementation Plan

Chapter III → the last section, after Test Evaluation Plan

Paste — Chapter III › Implementation Plan

Implementation proceeds in four stages, ordered so that each depends only on what precedes it.

Backend deployment

The Cloud Functions, the Firestore security rules and the database indexes are deployed first, to the asia-southeast1 region. The backend is deployed before either client because both clients and the controller depend on it, and because a client released against an undeployed function fails in a way the user cannot act on. Scheduled jobs are configured to the Manila timezone so that daily and monthly boundaries fall where the user’s billing period does.

Hardware preparation

The controller is assembled, the firmware is flashed, and a device identifier and token are issued and recorded against the account that will own it. The unit is bench tested against a reference meter before it is placed in service. Mains connections are made by the researchers.

Client release

The Android package is produced by the continuous integration pipeline from a recorded commit and published as a versioned release, from which users install it directly; distribution through an application store is outside the scope of this study. The web dashboard is deployed to static hosting under the project domain, and its download link is updated to the version just released so that the two remain in step.

User onboarding

The user installs the application, registers an account and verifies the address, connects the Hub to the household wireless network through the setup portal, and pairs it by scanning the code on the unit. Rate figures are entered once from the household’s own billing statement so that computed cost reflects the tariff actually charged. A printed setup booklet accompanies the unit, and the interface states the next required step at each stage so that onboarding does not depend on the booklet being to hand.

Post-deployment

Faults reported by users are addressed by correction and re-release rather than by on-site intervention, since the clients update independently of the hardware. Backend usage is monitored against a configured budget threshold.
