WattWise Data Dictionary

Every field the running system writes, typed as Firestore actually stores it. Built to sit beside the corrected ERD, and to survive a panel member opening the Firebase console mid-defence.

Short answer

The dictionary you photographed belongs to Pananam, a different capstone on a relational database. It is a fine format to borrow and a dangerous one to copy, because every column in it encodes an assumption that is false for WattWise. Below is the dictionary in that same shape, with the types corrected to what the system stores.

Your ERD and this dictionary now agree. They did not before: the ERD was verified on 19 August and nine fields have been renamed, retyped, or added since. Those are listed further down, so you can correct the ERD rather than discover the gap during questioning.

Why the relational template cannot be copied straight across

Four assumptions in the Pananam tables, and what each becomes here. These are the rows a panel member with database experience will stop on.

Keys are strings, never integers ID · Int(10) · PK

Firestore document IDs are strings, and WattWise's carry meaning: a user is keyed by their Firebase Auth UID, an outlet by the literal "outlet1", a daily rollup by "2026-08-28", a budget by "2026-08". There is no auto-increment integer anywhere in the system.

Writing Int(10) in the dictionary is not a rounding error — it describes a database WattWise does not have, and one console screenshot disproves it.

Numbers are stored as numbers EstimatedHarvest · Varchar(100)

Pananam types nearly every field Varchar(100), harvest quantities included. WattWise cannot: energy, power, voltage, current and every peso amount are Firestore number fields, and the accuracy claims in Chapter IV are arithmetic performed on them directly.

A dictionary that types totalEnergy as text invites the obvious question of how you summed it.

The path is the foreign key FarmerID · Int(10) · FK1

A relational child table needs a FarmerID column to say who owns the row. In Firestore the location says it: users/abc123/outlets/outlet1 already encodes ownership, so there is no userId field on the outlet document and adding one would be redundant.

This is why the Firestore path column below is load-bearing rather than decorative. Only four genuine foreign keys survive — references to an outlet carried as an ordinary field, because the document does not live under that outlet.

Maps and arrays have no relational equivalent — no column type —

Several WattWise fields are structured values: thresholds is a nested map, applianceProfiles and pushTokens are arrays, applianceBreakdown is an array of maps. A relational schema would normalise each into its own table.

Keeping them inline is deliberate and defensible — an appliance profile is meaningless apart from its user, and reading a user's thresholds should not cost a join. Type them map and array, and say why in the description column.

One more thing worth noticing rather than copying: in Pananam's own CropClassification table, CropName is marked FK1 although it is that table's own descriptive name, and tblCrop.CropClassification is marked FK3 while typed Varchar(100) rather than as the integer key it would have to reference. Mis-marked keys are the most common defect in a data dictionary. Check every FK below against the path column — each one should point at a document that genuinely exists elsewhere.

One thing neither document currently mentions

There is a Realtime Database write in the command path

When a command is dispatched, deviceCommandDispatcher.js writes the Firestore document and then attempts a second write to the Firebase Realtime Database at devices/{deviceId}/commands/{outletId}. On success it records delivery.channel = "firestore+rtdb"; on failure it logs a warning, sets "firestore", and carries on.

Nothing reads it. The firmware calls exactly three URLs — updateOutletMetrics, getDeviceCommand and ackDeviceCommand — all Cloud Functions over HTTPS. There is no Realtime Database client in the sketch, and firebase.json declares no database, no rules file and no instance. It is a leftover from the original push-based design that the poll-based flow replaced.

You do not need to document it as an entity, and you should not draw it on the ERD. You do need to be able to answer it, because a panel member browsing the Firebase console may find a Realtime Database node sitting there. Settle it before the defence: open any recent document under device_commands and read delivery.channel. If every row says "firestore", the write has been failing all along and the node is empty. If any says "firestore+rtdb", it is landing, and one sentence in Chapter III should say it is a redundant dispatch mirror that no client consumes.

Making the claim checkable

The value of a data dictionary at a defence is that it can be opened and compared. Four checks, in the order a panel would run them.

  1. Open one document of each kind. Firebase console → Firestore → users → your UID. Every path in the tables above appears as a literal folder name. If a path is wrong, it is wrong visibly and immediately.
  2. Check one field name character for character. currentStage, not stage. monthlyBudget, not budgetAmount. These are the rows a careful reader spot-checks.
  3. Confirm a type by its colour. The console renders numbers, strings, booleans and maps distinctly. Every field typed number here should render as a number there — that is the check that disproves the Varchar(100) habit.
  4. Show that the path is the key. Open users/{uid}/outlets/outlet1 and point out there is no userId field on it. That single observation carries the whole argument for why this dictionary is not shaped like Pananam's.

If you are asked why an ERD at all for a document database

The entities and their relationships are real regardless of the store. What changes is that the subcollection path is the foreign key. Everything a relational schema would express as a userID column, Firestore expresses as location — which is why USER is the parent in the diagram rather than a column on every table, and why only four true foreign keys appear in this dictionary.
